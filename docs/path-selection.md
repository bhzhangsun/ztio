## 1. 原则

| 原则 | 说明 |
|---|---|
| **并行，不串行** | 所有候选同时探测。串行等待会让用户感知为卡顿 |
| **先通则赢** | 第一个成功的就是当前路径，不等待「理论上更优」的候选 |
| **真实连接，不用 ICMP** | 只有 TCP 握手成功才证明「这个地址上的这个端口真的有你的 App 在听」 |
| **双向同时发起** | 见 §2 —— 这是 IPv6 路径能否成立的**关键** |
| **不丢弃落选者** | 未选中的成功候选保留为**温候选**，用于自愈 |
| **不扫描子网** | 只探测信令交换来的候选 |

## 2. 探测

对**候选集中的每一个候选**发起一次真实的连接尝试。

| 候选类型 | 探测方式 |
|---|---|
| IPv6 / IPv4 / ZT | TCP `connect()` 到 `addr:port`，带超时 |

**为什么不用 ICMP 或自制 UDP 探针**：

- ICMP 常被防火墙屏蔽 → 会产生**假阴性**
- 自制 UDP 探针无法确认对端**应用层**是否就绪
- 只有 TCP 握手成功才证明对端 App 确实在监听

### ⚠️ 必须双向同时发起，不能单向 connect

**这是 IPv6 路径能否成立的关键。** 背景见 [`protocol.md` §1.1](protocol.md#11-连通性的现实ipv4-与-ipv6-是两个不同的问题)。

- IPv6 **没有 NAT**，但两端的**状态防火墙默认阻断未请求的入站连接**
- 家用路由器默认阻断入站 IPv6；移动运营商普遍对入站做过滤
- 状态防火墙只放行**有状态的返回流量** —— 即**本端必须先有出站包，对端的入站包才会被放行**

**因此单向 `connect()` 在 IPv6 路径上会失败**：
A 连 B，B 的防火墙丢弃入站 SYN，因为 B 从未向 A 发过包。

```
   Mac                              手机
    │── connect(手机的 IPv6) ──────>│    ← 我的出站包，在我家防火墙开了洞
    │<────── connect(Mac 的 IPv6) ──│    ← 对端的出站包，在我家防火墙开了洞
    │                               │
    └──── 两侧的洞都开了 → 握手完成 ──┘
```

> **这与 IPv4 打洞是同一个机制**（simultaneous open），
> 区别在于 IPv4 还要额外解决地址变换，而 IPv6 **只需要开洞** —— 所以它是确定的。

**这个要求在本协议中自然满足**，因为候选交换是双向的（不变量 I2），
双方拿到对方候选后**都**会发起探测。**但它必须被显式保证，不能依赖巧合**：

| 保证方式 | 说明 |
|---|---|
| 收到候选集后**立即**开始探测 | 由信令驱动，不等待、不排队 |
| **不设「先连方」角色** | 没有 client/server 之分，避免一方只监听不发起 |
| 窗口内**重试 1 次** | 覆盖两端启动时间差（`PROBE_CONNECT_RETRIES`） |

### 并行度

**全部候选同时发起**，并发上限 `PROBE_MAX_CONCURRENCY`（默认 16）。
候选数量本身有上限（`CANDIDATE_MAX_COUNT`，默认 16），所以通常是全并发。

### 时间预算

```
t=0ms      ─┬─ 探测 lan-v6  ─┐
            ├─ 探测 lan-v6ll ─┤
            ├─ 探测 lan-v4   ─┼─→ 任一个成功 → 立即选定并返回
            ├─ 探测 zt       ─┤   全部失败     → 降级（§4）
            └─ ...           ─┘
t=1500ms   ── 单候选超时（PROBE_TIMEOUT）
t=2000ms   ── 探测窗口关闭（PROBE_WINDOW）＝ 直连预算 DIRECT_PROBE_BUDGET
```

**`DIRECT_PROBE_BUDGET` 是硬约束**：它是「用户感知」与「探测充分性」的平衡点。

### 探测结果记录

| 结果 | 含义 |
|---|---|
| `ok` | 握手成功，记录 RTT |
| `timeout` | 无响应 —— **包被丢弃** |
| `refused` | 收到 RST —— **主机可达，端口没开** |
| `unreachable` | 系统层明确不可达（无路由） |

> **`timeout` 与 `refused` 的区别是诊断的关键** —— 见 §4。

## 3. 选路

### 排序分两步

**先分档（决定成本），档内按实测 RTT（决定快慢）。**

| 档 | 路径 | 成本 |
|---|---|---|
| **① 直连** | IPv6 直连、局域网直连、IPv4 直连 | **0** —— 不出本链路，或不经服务器 |
| **② ZT DIRECT** | 打洞成功的 ZT 路径 | 双方上行流量 |
| **③ ZT RELAY** | 经 planet 中继 | **服务器流量费** |

### 选定规则

1. 在**探测窗口内成功的候选**中，取**最高档**
2. **同档内取 RTT 最小者** —— ❗ **不按地址族排序**
3. 若窗口内无成功候选 → 进入降级流程（§4）

> ### 为什么档内按 RTT 而不按地址族
>
> **IPv6 优先的理由是「没有 NAT、更可能成功」—— 那是可达性的论据，不是性能的论据。**
>
> 一旦多个候选**都**探测成功，可达性已经被实测证明了。
> 此时把 IPv6 固定排在 IPv4 前面，等于用一个「它更可能通」的先验
> 去推翻「它实测更慢」的事实 —— 在两者都通的情况下可能反而选慢的那条。
>
> **候选的 `priority` 字段用于**：探测发起顺序、RTT 相同时的 tiebreak、上层策略覆盖。
> 而**不用于**同档内的最终排序。

### 「同链路」的判定

| 地址族 | 判定 |
|---|---|
| IPv4 | 对端地址与本机某接口地址**在同一子网**（按该接口 netmask） |
| IPv6 | 对端地址与本机某接口地址**前缀匹配**（通常是 `/64`） |

同一链路内的路径延迟最低（通常 < 5 ms）且完全免费。
但它与跨网直连同属「① 直连」档 —— **若同链路候选失败而跨网 IPv6 成功，直接选后者，不降级到 ZT**。

### 温候选

**未选中的成功候选进入「温」状态，不丢弃。**

- 不维持长连接（省电、省资源）
- 记录最近成功时间
- **网络变化事件触发时立即重新探测**

> 这是与 ICE 最大的差异。ICE 选定后丢弃其余候选；
> ztio 保留它们，因为直连路径随时会因换网络而失效。

## 4. 降级

```
① 任一直连候选成功（IPv6 / 同链路 / IPv4）→ 用直连        （最优）
② 直连全失败，ZT DIRECT 成功              → 用 ZT DIRECT
③ 只有 ZT RELAY 可用                      → 用 ZT RELAY   （兜底）
④ 全部失败                                → ERROR
```

**降级是自动的、无损的**：应用层 API 与语义完全不变。

**关键约束**：降级**不能阻塞**数据面。
即使当前走 ZT RELAY，一旦某个直连候选恢复正常，**应当能切回去**（§5）。

### 直连全失败但 ZT 可用时的诊断

这种情况**必须记录并上报**，因为成因有多种，处置方式各不相同：

| 成因 | 可观测证据 | 可否修复 |
|---|---|---|
| **IPv6 入站被阻断** | 探测超时 | ⚠️ **先确认不是实现问题** —— 见下 |
| **客户端隔离**（AP isolation） | 同链路探测全部超时（无 RST） | ❌ 无解，接受降级 |
| **权限被拒**（iOS / macOS） | 系统回调明确返回拒绝 | ✅ 引导用户授权 |
| **对端未监听 / 端口错** | 收到 RST（`refused`） | ✅ 配置问题 |
| **对称型 NAT**（IPv4 路径） | 地址交换成功，但映射不可预测 | ❌ 无解，改走 IPv6 |

**这些表现不同，不能混淆**：权限与配置问题可修复，隔离与对称 NAT 不可修复。
如果混为一谈，用户会反复授权却毫无效果。

> **⚠️ 第一行尤其要注意。**
> IPv6 直连失败**最常见的实现原因**是探测写成了单向 `connect()` ——
> 两端的防火墙都不放行未请求的入站包（§2）。
> **在归因于运营商之前，先确认同时发起是否正确实现。**

## 5. 自愈

### 触发条件

| 事件 | 来源 | 动作 |
|---|---|---|
| 系统网络变化 | `NWPathMonitor` / `ConnectivityManager` | 重新枚举 → 重新探测 |
| 收到 `candidates-update` | 信令 | 更新候选 → 重新探测 |
| 当前路径连续失败 | `PATH_LOST_THRESHOLD` | 切换到温候选，或重新探测 |
| ZT 链路状态变化 | libzt 事件 | 重新评估档位 |

### 流程：先探测，后切换

```
1. 保留当前路径继续承载数据        ← 不中断
2. 后台并行探测新环境下的全部候选
3. 选出最优可用路径
4. 若优于当前路径（满足滞后条件）→ 切换（§6）
5. 否则继续用当前路径
```

**核心原则：任何时刻都有一条可用路径。** 探测在后台进行，不阻塞数据面。

### 去抖

网络变化可能短时间内连续触发（例如 WiFi 关联过程中的多次事件）。

- 合并 `CANDIDATE_DEBOUNCE`（500 ms）内的重复事件
- `RESELECT_MIN_INTERVAL`（2000 ms）内的重复重探测直接丢弃

## 6. 切换协议

### 为什么需要协议而非单方决定

**本端认为可用的路径，对端不一定在监听。**
如果单方切换，会出现「我切过去了，但对端没收到」的黑洞。

### 切换流程

```
A                                         B
│── switch{to: "192.168.1.23:45231"} ───>│
│                                         │ 验证该候选自己也在监听
│<───────── ack / nack ───────────────────│
│                                         │
│  收到 ack → 切换数据面                    │
│  收到 nack → 保持原路径，标记该候选不可用   │
│  超时      → 保持原路径                   │
```

### 滞后（hysteresis）

**不因为「略好一点」就切换** —— 切换本身有成本（重连、丢包、TLS 重协商）。

| 规则 | 值 |
|---|---|
| 需**严格更优**才切换 | 档位更高即可；同档需 RTT 优势 > 30% |
| 切换后冷却 | `SWITCH_COOLDOWN` 3000 ms |

**例外：当前路径**彻底失效**时立即切换，不受滞后约束。**

### 切换时的状态保持

| 状态 | 处理 |
|---|---|
| 信令会话 | **保持**（走 ZT，与数据路径无关）—— 见不变量 I1 |
| 应用层连接 | 上层决定：重建，或由上层做数据缓冲 |
| 探测结果 | 保留（温候选） |

> **ztio 不替应用层做连接迁移。** 它只负责「路通了」，
> 连接语义（重传、续传、重连）属于应用层。

## 7. 边界

**ztio 负责**：地址交换、连通性探测、路径选择、失败降级、网络变化后自愈。

**ztio 不负责**：NAT 穿透算法（交给 ZeroTier）、虚拟网卡 / 系统路由、
应用层的数据可靠性与连接迁移、跨用户的公共网络。

### 明确不做：出口选路

「让手机的流量从 Mac 的宽带出去」这类**出口选路**是**应用层**的事：

- 它需要在应用的数据收发逻辑里显式绑定接口
- 各平台机制完全不同（Android `bindProcessToNetwork` 是进程级；
  iOS `NWParameters.requiredInterfaceType` 是连接级）
- ztio 只负责把**路径**建好，不干预**应用如何使用它**

详见 [`../app/platform.md`](../app/platform.md)。
