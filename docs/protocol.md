# ztio 协议规范

ztio 是**一套协议**，不是某一个 SDK。
它规定「两台各自运行自有 App 的设备，如何在 ZeroTier 之上建立尽可能直连的连接」。

各平台对同一套协议的**实现与授权必然分叉** —— 见 [`../app/platform.md`](../app/platform.md)。

## 1. 问题

两台设备（典型：Mac 与手机）各跑一个自有 App，需要建立可靠连接。现实约束：

1. **两者经常在同一个局域网内** —— 走公网绕一圈是浪费
2. **受限网络普遍屏蔽组播/广播** —— mDNS、SSDP、UDP 广播发现全部失效
3. **可达性取决于双方的地址族与网络类型** —— 见 §1.1，这是最核心的约束
4. **不能依赖需要公网暴露的发现服务** —— 增加运维负担、单点、且会把内网拓扑送到公网
5. **不能要求用户手动填 IP** —— 地址由 DHCP 分配、随时变化

### 1.1 连通性的现实：IPv4 与 IPv6 是两个不同的问题

> **关键认识：IPv4 和 IPv6 面临的不是同一个问题，而真正麻烦的那个只存在于 IPv4。**

| | IPv4 | IPv6 |
|---|---|---|
| 地址变换 | ✅ 有 NAT，且常有多层 | ❌ **没有 NAT**（NAT66 罕见） |
| 地址稀缺 | ✅ 稀缺 → CGNAT / 多层 NAT | ❌ 每个主机一个 `/128` |
| 入站阻断机制 | NAT **加** 防火墙 | **仅防火墙** |
| 打洞涉及什么 | 地址变换 **加** 开洞 | **只涉及开洞** |
| 打洞是否确定 | ❌ 取决于 NAT 类型，不可预测 | ✅ **确定、可预测** |

**IPv4：真正的问题是对称型 NAT**

| NAT 类型 | 打洞 | 特征 |
|---|---|---|
| Full-cone / Address-restricted cone / Port-restricted cone | ✅ 能 | **Endpoint-Independent Mapping**（映射一致） |
| **Symmetric（对称型）** | ❌ **不能** | 对每个目标给出**不同**的映射 |

**而对称型恰恰是主流默认配置**：

> Symmetric NAT-like issues, **which is the majority of default NAT configuration out there,
> even on CGNAT products** —— [ipSpace.net](https://blog.ipspace.net/2025/04/response-nat-traversal)

**另一类失败场景是「同一个 NAT 后的两台设备」**：需要路由器支持 NAT hairpin（loopback）。
它**不是**必然失败，而是**依赖路由器能力**，因此不可预测。

**IPv6：没有 NAT，但仍然要打洞**

「有 IPv6」不等于「天然可达」。两端的**状态防火墙**仍然阻断未请求的入站连接：

- **家用路由器**：默认阻断所有未请求的入站 IPv6 ——
  "Routers aimed at the consumer space **block inbound IPv6 by default**, you have to explicitly open it up"
  （[来源](https://oneuptime.com/blog/post/2026-03-20-ipv6-firewall-home-routers/view)）
- **移动运营商**：普遍对入站连接做过滤

**但 IPv6 的打洞要简单得多**，因为不涉及地址变换：

> There are **two separate problems** with IPv4 and **only one applies to IPv6**.
> Allowing incoming connections through a restrictive firewall is applicable to both.
> **Address mangling via NAT applies only to one.**
> —— [Hacker News](https://news.ycombinator.com/item?id=47384032)

> Decent stateful firewalls match on the full 5-tuple, which is functionally equivalent to symmetric NAT,
> but **don't change the UDP port numbers** when packets traverse them...
> **Firewall hole punching only involves STUN, and that's it.**
> —— [ipSpace.net](https://blog.ipspace.net/2025/04/response-nat-traversal)

**结论**：IPv6 的入站阻断是**有状态防火墙**，靠**双方同时发起**即可打通 ——
不涉及地址变换，因而是确定的。与 IPv4 对称型 NAT 的「原理上不可行」有本质区别。
**同时发起的机制见 [`path-selection.md`](path-selection.md#2-探测)。**

**现实中的典型组合**

| 设备 | 典型网络 | IPv4 | IPv6 |
|---|---|---|---|
| 手机 | WiFi 或蜂窝 | 对称型 NAT / CGNAT | ✅ 通常有 |
| 家庭服务器 | 家宽 | 锥形 NAT | ✅ 通常有 |
| Mac | 任意 | 视网络 | ✅ 通常有 |

**两端都有 IPv6 是常态** —— 通常存在一条 IPv6 直连路径，比任何 NAT 打洞都更确定。

### 1.2 问题的本质：发现与可达是两层

| 层 | 问题 | 典型机制 | 受限网络下 |
|---|---|---|---|
| **发现** | 对方的**地址**是多少？ | mDNS / 广播 / 服务器下发 | ❌ **最常被屏蔽** |
| **可达** | 往那个地址发包能到吗？ | 单播（可能需同时发起） | ✅ 多数情况下是好的 |

**ztio 的大部分工作，是用一条能通的通道（ZT 链路）去送「发现」这一层的信息，
从而让本来就没坏的「可达」这一层发挥作用。**

> **注意 §1.1 带来的修正**：可达这一层**并非无条件好**。
> IPv6 路径上两端的防火墙都要求**出站包先开洞**，所以探测必须**双向同时发起**。

## 2. 分层与四个抽象

```
┌──────────────────────────────────────────────────────┐
│  L4  应用层        App 逻辑，只调 ztio.connect(peer)  │
├──────────────────────────────────────────────────────┤
│  L3  路径选择      按档位 + 实测 RTT 选路，失败降级     │
├──────────────────────────────────────────────────────┤
│  L2  候选集        本机枚举出的地址 + ZT 地址          │
├──────────────────────────────────────────────────────┤
│  L1  信令          经 ZT 链路交换候选集与状态          │
├──────────────────────────────────────────────────────┤
│  L0  ZT 传输       身份 / 加密 / 地址 / 兜底可达性     │
└──────────────────────────────────────────────────────┘
        ▲ 引导（Bootstrap）：经锚点解析 peerName → ZT 地址
```

**每一层只依赖下一层。** 唯一的外部依赖是 L0 的 ZeroTier 部署。

### 四个抽象（与 ICE 的对应）

| ztio | ICE 对应 | 职责 |
|---|---|---|
| **Signaling** | 信令通道 | 交换候选集；在 ztio 中就是 **ZT 链路本身** |
| **Candidate** | Candidate | 一个可被连接的地址；由设备**自行枚举** |
| **Connectivity Check** | STUN / 连接检查 | 对候选发起**双向**连接，测量可达性 |
| **Path Selection** | pair 排序与提名 | 按档位 + RTT 选定路径，其余保留备用 |

**与 ICE 的关键差异**

| | ICE | ztio |
|---|---|---|
| 信令通道 | 需外部提供（SIP / WebSocket / 自建） | **ZT 链路自带** |
| 地址发现 | STUN 服务器告知公网映射 | **设备自行枚举**（含局域网与 IPv6） |
| 未选中的候选 | 丢弃 | **保留为温候选**，随时可切 |

> **最后一行最重要。** ztio 不丢弃未选中的候选 ——
> 直连路径随时会因换网络而失效，保留候选使**自愈**无需重走完整流程。

### 前提假设

| # | 假设 | 不成立时 |
|---|---|---|
| A1 | ZeroTier 链路**至少能经 relay 建立** | 整个方案不成立（无信令通道） |
| A2 | 各设备可访问自建 planet | 同上 |
| A3 | 设备能枚举自己的网络接口 | 无候选，退化为纯 ZT 路径 |
| A4 | 用户已授予局域网访问权限 | 退化为纯 ZT 路径（**正常降级，非错误**） |

> **A1 是地基。** 正因为 ZT 提供了「最差也能通」的通道，
> 才使得「不需要任何公网发现服务」成为可能。

## 3. 引导（Bootstrap）

### 要解决的问题

要用 ZT 链路交换候选，前提是**能连上对端**。但「连上对端」需要知道对端的 ZT 地址 —— 鸡生蛋。

**引导只解决一件事：`peerName → ZT 地址`。**

### 为什么这一层比局域网发现容易得多

| | 局域网 / IPv6 地址 | ZT 地址 |
|---|---|---|
| 谁分配 | 上游 DHCP / RA，随机 | **你的 controller** |
| 是否稳定 | ❌ 换网就变 | ✅ 加入网络后固定 |
| 是否可预知 | ❌ 无法预知 | ✅ **可编排、可预分配** |
| 有无固定入口 | ❌ 无 | ✅ **有：网络网关** |

**所以这一层不需要「动态发现」，只需要「查表」。**

### 锚点模型

```
        ZT 叠加网（私有，加密）
   ┌──────────────────────────────────┐
   │   ┌─────────────┐                │
   │   │  锚点        │  172.16.0.1    │  ← 地址固定，常开
   │   │  花名册      │  名字解析       │
   │   └──────┬──────┘                │
   │   ┌──────┴──────┐                │
   │  Mac          手机                │
   │  172.16.0.12  172.16.0.11        │
   └──────────────────────────────────┘
```

| 性质 | 说明 |
|---|---|
| **地址固定** | 由 controller 静态分配（如 `172.16.0.1`），所有设备天然知道 |
| **只在网内可达** | 不暴露任何端口到公网 |
| **无状态即可用** | 花名册可以只是一个静态配置文件 |

**谁当锚点**：网络中任何一台常开设备。通常就是**网段网关** ——
它本来就在每台设备的配置里（作为 DNS 服务器和默认路由），不需要额外告知。

**两种实现**

| 方式 | 做法 | 适合 |
|---|---|---|
| **A. 静态花名册** | 锚点上维护 `name → ZT 地址` 配置文件，设备直接读 | **设备数量固定（推荐起步）** |
| **B. 动态注册** | 锚点提供**只绑 ZT 接口**的 HTTP 端点：`POST /register`、`GET /lookup`、`GET /roster`，带 TTL 续约 | 设备数量增长、地址动态分配 |

**方式 B 的认证**：复用 ZT 网络本身的私有性 —— 端点只绑在 ZT 接口地址上，网外不可达。

### 缓存策略

| 项 | 值 | 理由 |
|---|---|---|
| 映射缓存 TTL | 300 s | ZT 地址极少变 |
| 失败退避 | 指数，上限 60 s | 避免锚点故障时打爆 |
| **动态候选缓存** | **不缓存** | 局域网 IP 与 IPv6 都会变，**每次连接前必须重新交换** |

> **最后一条是硬性要求。** ZT 地址可以缓存，**动态地址绝对不能** ——
> 混淆它们会导致「换网络后连不上」的经典故障。

### 失败与降级

| 失败点 | 处置 |
|---|---|
| 锚点不可达 | 用本地缓存映射重试；缓存过期则报「引导失败」 |
| 名字不存在 | **终止** —— 这是配置错误，不是网络问题 |
| 注册失败 | **不阻断** —— 自己能发起连接就够了 |

> **引导失败不应等于「整个不可用」。** 只要能查到对端，自己不需要可被查到。

## 4. 候选（Candidates）

### 原则

> **设备自己最清楚自己有哪些地址。不要问服务器「我的 IP 是什么」。**

服务器只能看到**公网映射**，看不到局域网地址、多个接口、IPv6 link-local ——
而这些恰恰是 ztio 最需要的。

### 枚举什么

**全部枚举，不预判哪个「应该能通」—— 那是探测的工作。**
下表只是**探测的发起顺序**（最终选路规则见 [`path-selection.md`](path-selection.md)）：

| 序 | 类型 | 示例 | 为什么排这个位置 |
|---|---|---|---|
| 1 | **IPv6 全局单播** | `2408:...::5` | **没有 NAT** —— 只需穿防火墙，确定且可预测 |
| 2 | **IPv6 link-local** | `fe80::1a2b:3c4d` | 同一链路直达，需配 scope id |
| 3 | **IPv4 私有地址** | `192.168.1.23` | 同链路直达，但仅限同网段，且依赖单播不被隔离 |
| 4 | **ZT 地址** | `172.16.0.11` | 兜底，永远存在 |
| 5 | IPv4 公网地址 | `203.0.113.7` | 若设备直接持有公网 IP 则最优；否则需穿透 |

> **这只是探测顺序，不是最终排序。** 多个候选都成功时由**实测 RTT** 决定。

### 必须过滤掉的

| 过滤项 | 原因 |
|---|---|
| `127.0.0.0/8`、`::1` | 回环 |
| `169.254.0.0/16` | IPv4 link-local，几乎不可用 |
| **TUN / TAP 接口**（含 ZT 自己的虚拟接口） | ❗ 否则会把 ZT 地址当成 LAN 候选，**信令逻辑自指** |
| IPv6 link-local **无 scope id** | 无法确定走哪个接口 |
| 状态为 `down` 的地址 | 显然不可达 |
| 组播 / 广播地址 | 不是可连接的单播目标 |

> **最容易出错的是 TUN/TAP 那条。** 不排除虚拟接口，
> 设备会把自己的 ZT 地址当作「局域网候选」报给对端，
> 对端探测它时**走的还是 ZT 链路** —— 于是「直连」这个优化静默失效，
> 且**从现象上完全看不出来**。

**接口名过滤模式**：`utun*` `tun*` `tap*` `zt*` `docker*` `veth*` `br-*` `vmnet*` `vboxnet*`

### 数据结构

```json
{
  "type": "lan-v4" | "lan-v6" | "lan-v6ll" | "zt" | "wan",
  "addr": "192.168.1.23",
  "scope": "eth0",
  "port": 45231,
  "priority": 30,
  "gen": 7
}
```

| 字段 | 必要性 | 说明 |
|---|---|---|
| `type` | 必须 | 决定优先级与探测方式 |
| `addr` | 必须 | 单播地址 |
| `scope` | link-local 必须 | 接口标识（iOS/Android 上通常是接口名） |
| `port` | 必须 | **每台设备的监听端口可以不同，必须交换** |
| `priority` | 必须 | 探测顺序 + RTT 相同时的 tiebreak。**不用于最终排序** |
| `gen` | 必须 | 候选集代数 |

### 端口策略

**每台设备在候选里带上自己的监听端口** —— 移动端无法保证固定端口（系统可能回收、可能被占用）。

| 平台 | 建议 |
|---|---|
| 桌面 | 固定端口 + 动态回退 |
| 移动端 | **纯动态**，每次启动重新分配并在信令中告知 |

### 候选集代数 `gen`

**问题**：手机从 WiFi 切到 4G，候选集完全变了；对端还拿旧候选探测会一直失败。

**方案**：每次候选集变化，`gen` 自增 1。

- 收到更高 `gen` → **丢弃旧候选，重探测**
- 收到更低或相同 `gen` → 忽略（防乱序）
- 断线重连后 `gen` 从 0 重新开始 → 用 `sessionId` 区分会话

```
(sessionId, gen) 共同构成候选集的版本标识
sessionId 变化        → 全新会话，所有旧状态作废
sessionId 相同 + gen++ → 增量更新，重探测
```

### 枚举时机

| 时机 | 动作 |
|---|---|
| 启动时 | 全量枚举 |
| 系统网络变化回调 | 全量重新枚举，`gen++`，立即推送 |
| 定期（30 s） | 轻量校验，**仅在发现变化时才推送** |
| 每条连接建立前 | **强制重新交换**（不使用任何缓存地址） |

**平台回调**：iOS `NWPathMonitor` / Android `ConnectivityManager.registerDefaultNetworkCallback()` /
桌面轮询 + 系统事件。详见 [`../app/platform.md`](../app/platform.md)。

### ⚠️ IPv6 地址会轮换

**IPv6 隐私扩展（RFC 4941）会定期更换源地址**，移动设备尤其明显。

| 影响 | 说明 |
|---|---|
| 候选会**自然过期** | 上一轮交换来的 IPv6 地址可能几分钟后失效 |
| **不能缓存** | 与局域网 IP 同理 |
| `gen` 机制正是为此而设 | 地址变化 → 重新枚举 → `gen++` → 推送 → 重探测 |

**这使 `CANDIDATE_RESCAN_INTERVAL`（默认 30 s）成为必要机制而非优化项。**

## 5. 信令与状态机

### 信令通道 = ZeroTier 链路本身

没有独立的信令服务器。信令只在**建连时**和**网络变化时**发生，数据量极小 ——
即使 ZT 退化到 RELAY，这点流量成本也可以忽略，而数据面走的是直连。

**信令会话**：在 ZT 地址之上建立一条连接，用于双向交换消息。
它天然加密、天然认证。

### 消息格式

统一信封：

```json
{ "v": 1, "sid": "7f3a9c21", "seq": 12, "type": "offer", "body": { } }
```

| 字段 | 说明 |
|---|---|
| `v` | 协议版本，不匹配则拒绝 |
| `sid` | 会话标识；变化即代表全新会话 |
| `seq` | 会话内单调递增，用于防重放与乱序检测 |
| `type` | 消息类型 |
| `body` | 类型相关载荷 |

### 消息类型

| 类型 | 方向 | 载荷 | 说明 |
|---|---|---|---|
| `offer` | 发起方 → 应答方 | `{peer, gen, candidates[]}` | 发起方发送自己的候选集 |
| `answer` | 应答方 → 发起方 | 同 `offer` | 应答方回应自己的候选集 |
| `candidates-update` | 单向推送 | `{gen, candidates[]}` | 候选集变更；**接收方必须立即重探测** |
| `probe-result` | 可选 | `{gen, addr, ok, rtt_ms}` | 反馈探测结果，省掉对端重复探测 |
| `switch` | 双向协商 | `{to, gen, reason}` | 路径切换通知；接收方须确认该候选可用 |
| `ping` / `pong` | 双向 | `{ts}` | 维持信令会话，检测其存活 |
| `error` | 双向 | `{code, msg}` | 例：`no-common-path` |

**示例**

```json
{
  "type": "offer",
  "body": {
    "peer": "mac",
    "gen": 7,
    "candidates": [
      {"type":"lan-v6","addr":"2408:8207::5","port":45231,"priority":10},
      {"type":"lan-v4","addr":"192.168.1.23","port":45231,"priority":30},
      {"type":"zt","addr":"172.16.0.12","port":45231,"priority":40}
    ]
  }
}
```

### 状态机

```
   IDLE ──zts_net_join──> JOINING ──network-ok──> BOOTSTRAP ──resolved──> SIGNALING
                                                                              │
                                                                    candidates ×2
                                                                              ▼
   ERROR <──全部失败──────────────────────────────────────────────────── PROBING
                                                                              │ first-ok
                                                                              ▼
                          RESELECT <──network-change / path-lost────── CONNECTED
                              │                                              ▲
                              └──────────── better-path ────────────────────┘
```

| 状态 | 进入条件 | 动作 | 退出条件 |
|---|---|---|---|
| `IDLE` | 初始 | —— | 调用 `connect()` |
| `JOINING` | 已发起入网 | 等 libzt 网络就绪 | 拿到 ZT 地址 |
| `BOOTSTRAP` | 已入网 | 查花名册 | 解析成功 / 用缓存 |
| `SIGNALING` | 已解析地址 | 建信令会话、交换候选 | 双方候选集齐备 |
| `PROBING` | 候选集齐备 | 双向并行探测 | 任一成功 / 全部失败 |
| `CONNECTED` | 路径选定 | 数据面运行、保活 | 路径失效 / 网络变化 |
| `RESELECT` | 收到 change / 路径失效 | 重新枚举与探测 | 选出新路径 / 无路可走 |
| `ERROR` | 无法恢复 | 上报上层 | —— |

### 关键不变量

| # | 不变量 | 违反的后果 |
|---|---|---|
| I1 | **信令会话与数据路径生命周期独立** | 切换路径时信令断了，就无法再协商 |
| I2 | **候选集必须双向交换** | 单向会导致对端无法在直连路径上找到你 |
| I3 | **`gen` 只在候选集真正变化时递增** | 频繁递增会引发探测风暴 |
| I4 | **收到的候选集不持久化** | 隐私泄露 |
| I5 | **切路径前必须确认对端可接受** | 会切到对端不监听的地址 |
| I6 | **信令失败不等于连接失败** | 只要有一条可用路径，数据面就应继续 |

> **I1 最容易写错**：很多实现把信令连接和数据连接做成同一条，
> 结果一切换路径就失去协商能力，无法再切回来。

### 版本与兼容

| 项 | 策略 |
|---|---|
| 版本字段 `v` | 不匹配 → 拒绝并回 `error`，**不尝试兼容** |
| 未知 `type` | **忽略**（前向兼容），不报错 |
| 未知字段 | 忽略 |

**原则**：宁可拒绝一个不认识的版本，也不要猜测语义。

## 6. 安全

### 信任模型

```
信任根 = 自建 ZeroTier 网络
         ├─ 身份：网络成员身份（40 位 ZT 地址 + 密钥对）
         ├─ 加密：端到端，planet 也解不开
         └─ 授权：controller 的成员白名单（private=true）
```

**ztio 不引入新的信任根。** 它唯一新增的安全边界是：
**谁可以拿到我的地址集** —— 那是敏感信息，只应给已入网的、你信任的对端。

### 敏感信息

| 信息 | 敏感度 | 保护措施 |
|---|---|---|
| **候选集（全部本地地址）** | **高** | 只经 ZT 加密链路；不持久化；不写日志 |
| ZT 地址 | 中 | 花名册只在 ZT 网内可达 |
| 端口号 | 低 | 同上 |
| 出口 IP | 低 | 对端可见，不可避免 |

### 威胁与对策

| # | 威胁 | 对策 |
|---|---|---|
| T1 | **陌生成员窃取网络拓扑** —— 恶意成员发起信令骗取候选集 | **`private=true`（硬性要求）** + 只响应花名册中的名字 |
| T2 | **信令重放** —— 重放旧 `offer` 诱导回连失效地址 | `seq` 单调检查 + `gen` 版本检查 + `sid` 会话隔离 |
| T3 | **降级攻击** —— 阻断直连，迫使流量长期走 RELAY | **记录并上报降级原因**（可检测，不静默）+ 定期重探测 |
| T4 | **探测被当作端口扫描** | ✅ **只探测信令交换来的候选，永不扫描子网** |
| T5 | **锚点被入侵** —— 篡改花名册，把名字指向攻击者 | 锚点只提供 ZT 地址（攻击者仍需有效 ZT 身份）+ 地址异常变更告警 + **静态花名册攻击面最小** |
| T6 | **地址泄露到公网** —— 崩溃日志/分析上报带上候选集 | **候选集不写入任何日志**；诊断只上报计数 |

> **T4 是设计选择，不是限制。** 候选由信令给出，所以**永远不需要扫描子网** ——
> 既避免扫描观感，也避免触发企业网的安全告警。

### 隐私原则

| # | 原则 |
|---|---|
| P1 | **地址集不离开你自己的设备** —— 只在设备间经 ZT 加密链路交换 |
| P2 | **不引入公网发现服务** —— 减少数据外流面 |
| P3 | **不扫描子网** —— 只探测信令给出的候选 |
| P4 | **不持久化候选集** —— 内存中处理完即丢弃 |
| P5 | **诊断只上报计数与状态，不上报地址** |
| P6 | **降级不静默** —— 用户有权知道当前走的是哪条路径 |

> **P1 是本方案相对「公网 rendezvous」最大的隐私优势。**
> rendezvous 方案要求每台设备把自己的内网地址上报到一台公网服务器 ——
> 那台服务器因此持有了整个内网拓扑。

| 参数 | 默认值 | 说明 |

### 探测与选路

| 参数 | 默认值 | 说明 |
|---|---|---|
| `PROBE_TIMEOUT` | 1500 ms | **单候选探测超时** |
| `PROBE_WINDOW` | 2000 ms | **整体探测窗口** |
| **`DIRECT_PROBE_BUDGET`** | **2000 ms** | **直连路径的总预算（硬约束）** |
| `PROBE_MAX_CONCURRENCY` | 16 | 并发上限 |
| `PROBE_CONNECT_RETRIES` | 1 | 单候选重试（**覆盖两端启动时间差**） |

| `SWITCH_HYSTERESIS` | 1 档 | 需严格更优才切换 |

> **`DIRECT_PROBE_BUDGET` 是最重要的参数。**
> 它是「用户感知」与「探测充分性」的平衡点；超过它收益极小，代价是明显卡顿。

### 自愈

| 参数 | 默认值 | 说明 |
|---|---|---|
| `RESELECT_MIN_INTERVAL` | 2000 ms | 两次完整重探测最小间隔 |
| `PATH_HEALTH_PING` | 5000 ms | 数据面健康检查 |
| `PATH_LOST_THRESHOLD` | 3 | 连续失败即判失效 |
| `WARM_PROBE_INTERVAL` | 30000 ms | 温候选轻量重探测 |

### 诊断指标

| 指标 | 用途 |
|---|---|
| `probe.direct.success` / `.timeout` / `.refused` | **区分隔离与权限问题** —— 见下 |
| `probe.zt.direct` / `probe.zt.relay` | 判断 ZT 是否退化到中继 |
| `switch.count` / `switch.reason` | 判断网络是否不稳定 |
| `bootstrap.cache_hit` | 判断锚点是否健康 |

**`timeout` 与 `refused` 的区别是关键**：

- `refused`（收到 RST）→ 主机可达，端口没开 → **配置 / 端口问题**
- `timeout`（无响应）→ 包被丢弃 → **客户端隔离**（或权限被拒）

这个区分直接决定用户该做什么。
