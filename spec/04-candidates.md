# 04 · 候选枚举

## 4.1 原则

> **设备自己最清楚自己有哪些地址。不要问服务器「我的 IP 是什么」。**

服务器只能看到**公网映射**，看不到局域网地址、看不到多个接口、看不到 IPv6 link-local。
而这些恰恰是 ztio 最需要的。

## 4.2 枚举哪些地址

**全部枚举，不预判哪个「应该能通」—— 那是探测的工作。**
下表只是**探测的发起顺序**（最终选路规则见 `06-path-selection.md` §6.3）：

| 序 | 类型 | 示例 | 为什么排这个位置 |
|---|---|---|---|
| 1 | **IPv6 全局单播** | `2408:...::5` | **没有 NAT** —— 只需穿防火墙，确定且可预测 |
| 2 | **IPv6 link-local** | `fe80::1a2b:3c4d` | 同一链路直达，无需任何配置；需配 scope id |
| 3 | **IPv4 私有地址** | `192.168.1.23` | 同链路直达，但仅限同网段，且依赖单播不被隔离 |
| 4 | **ZT 地址** | `172.16.0.11` | 兜底，永远存在 |
| 5 | IPv4 公网地址 | `203.0.113.7` | 若设备直接持有公网 IP 则最优；否则需穿透 |

> **⚠️ 这只是探测顺序，不是最终排序。**
> 一旦多个候选**都**探测成功，最终由**实测 RTT** 在同档内决定
> —— 理由见 `06-path-selection.md` §6.3 的说明框。

**IPv6 排在最前不是偏好，是 `01-overview.md` §1.2 的结论**：

- IPv6 路径**不涉及地址变换**，两端的入站阻断只是**有状态防火墙**，
  靠**双方同时发起**即可打通（见 `06-path-selection.md` §6.2）
- IPv4 的**对称型 NAT** 是**原理上不可打洞**的 —— 对每个目标给出不同映射

**两者的差异不是「概率高低」，是「确定与不确定」。**

## 4.3 必须过滤掉的

| 过滤项 | 原因 |
|---|---|
| `127.0.0.0/8`、`::1` | 回环，只对本机有意义 |
| `169.254.0.0/16`（IPv4 link-local） | 无 DHCP 时的自分配地址，几乎不可用 |
| **TUN / TAP 接口**（含 ZT 自己的虚拟接口） | ❗ **否则会把 ZT 地址当成 LAN 候选，导致信令逻辑自指** |
| IPv6 link-local 但**无 scope id** | 无法确定走哪个接口，不可用 |
| 接口状态为 `down` 的地址 | 显然不可达 |
| 组播 / 广播地址 | 不是可连接的单播目标 |

> **最容易出错的是 TUN/TAP 那条**：如果不排除虚拟接口，
> 设备会把自己的 ZT 地址当作「局域网候选」报给对端，
> 对端探测它时走的**还是 ZT 链路** —— 于是「局域网直连」这个优化静默失效，
> 而且很难从现象上看出问题。

## 4.4 候选的数据结构

```json
{
  "type": "lan-v4" | "lan-v6" | "lan-v6ll" | "zt" | "wan",
  "addr": "192.168.1.23",
  "scope": "eth0",          // 仅 link-local 需要
  "port": 45231,            // 本端监听端口
  "priority": 30,           // 见 4.2 的排序
  "gen": 7                  // 候选集代数，见 4.6
}
```

**字段说明：**

| 字段 | 必要性 | 说明 |
|---|---|---|
| `type` | 必须 | 决定优先级与探测方式 |
| `addr` | 必须 | 单播地址 |
| `scope` | link-local 必须 | 接口标识（iOS/Android 上通常是接口名） |
| `port` | 必须 | **每台设备的监听端口可以不同**，必须交换 |
| `priority` | 必须 | 探测顺序 + RTT 相同时的 tiebreak。**不用于同档内的最终排序** —— 见 06 §6.3 |
| `gen` | 必须 | 见 4.6 |

## 4.5 端口策略

**每台设备在候选里带上自己的监听端口。** 理由：

- 移动端无法保证固定端口（系统可能回收、可能被占用）
- 端口随进程生命周期变化
- 因此**端口必须是候选的一部分，不能硬编码**

**监听策略**：

| 平台 | 建议 |
|---|---|
| 桌面 | 固定端口 + 动态回退 |
| 移动端 | **纯动态**，每次启动重新分配并在信令中告知 |

## 4.6 候选集代数（`gen`）

**问题**：手机从 WiFi 切到 4G，它的候选集完全变了。对端如果还拿旧候选去探测，会一直失败。

**方案**：每次候选集发生变化，`gen` 自增 1。

- 对端收到更高 `gen` 的候选集 → **丢弃旧候选，用新的重探测**
- 收到更低或相同的 `gen` → 忽略（防乱序）
- 断线重连后 `gen` 从 0 重新开始 → 用 `sessionId` 区分不同连接会话

**`gen` 与 `sessionId` 配合**：

```
(sessionId, gen) 共同构成候选集的版本标识
sessionId 变化 → 全新会话，所有旧状态作废
sessionId 相同 + gen 变大 → 增量更新，重探测
```

## 4.7 枚举时机

| 时机 | 动作 |
|---|---|
| 启动时 | 全量枚举 |
| 系统网络变化回调触发 | 全量重新枚举，`gen++`，立即推送 |
| 定期（30s） | 轻量校验，**仅在发现变化时才推送** |
| 每条连接建立前 | **强制重新交换**（不使用缓存的地址） |

### ⚠️ IPv6 地址会轮换

**IPv6 隐私扩展（RFC 4941）会定期更换源地址**，手机等移动设备尤其明显。

| 影响 | 说明 |
|---|---|
| 候选会**自然过期** | 上一轮交换来的 IPv6 地址可能在几分钟后失效 |
| **不能缓存** | 与局域网 IP 同理，每次连接前必须重新交换 |
| `gen` 机制正是为此 | 地址变化 → 重新枚举 → `gen++` → 推送 → 重探测 |

**这提高了 `CANDIDATE_RESCAN_INTERVAL`（默认 30s）的重要性** ——
它不是「优化」，而是**跟上地址轮换的必要机制**。
见 `07-parameters.md` §7.3。

**iOS**：`NWPathMonitor`
**Android**：`ConnectivityManager.registerDefaultNetworkCallback()`
**桌面**：轮询 + 系统事件（各平台不同，见 08）

## 4.8 安全考量

候选集包含设备的**全部网络地址** —— 这是敏感信息。

| 措施 | 说明 |
|---|---|
| **只经 ZT 加密链路传输** | 绝不上报公网服务 |
| **只发给已认证的对端** | 信令会话建立在 ZT 网络成员身份之上 |
| **不持久化** | 收到的候选集只在内存中保留，进程退出即丢弃 |
| **`gen` 防重放** | 拒绝旧代数的候选集，避免被诱导回连已失效地址 |

详见 `09-security.md`。
