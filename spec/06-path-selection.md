# 06 · 连通性检查与路径选择

## 6.1 核心原则

> **并行探测，先通则赢；优先级只用于排序，不用于串行等待。**

串行尝试（先试 LAN、超时后再试 ZT）会让首选项失败时的等待时间累加，
用户感知为卡顿。**正确做法是所有候选同时探测，取最先成功且优先级最高的那个。**

---

## 6.2 探测

### 探测什么

对**候选集中的每一个候选**发起一次真实的连接尝试。

| 候选类型 | 探测方式 |
|---|---|
| LAN / WAN | TCP `connect()` 到 `addr:port`，带超时 |
| ZT | 同上（走 ZT 接口） |

**用真实连接探测，不要用 ICMP 或自制 UDP 探针**：

- ICMP 常被防火墙屏蔽，会产生假阴性
- 自制 UDP 探针无法确认对端**应用层**是否就绪
- 只有 TCP 握手成功才证明「这个地址上的这个端口真的有你的 App 在听」

### 并行度

| 项 | 建议值 |
|---|---|
| 最大并发探测数 | 不限（候选数量通常在 10 以内） |
| 单候选超时 | **1500 ms** |
| 整体探测窗口 | **2000 ms**（超时后不再等待慢的候选） |

**为什么是 1500 ms**：局域网 RTT 通常 < 5 ms，即使算上 TLS 握手
和一次应用层问候，1500 ms 也有两个数量级的余量。
**局域网探测超过 1.5 秒基本等于失败。**

### 探测结果记录

```json
{ "candidate": "lan-v4:192.168.1.23:45231", "ok": true, "rtt_ms": 3, "at": 1736899200 }
```

**保留失败的记录**：用于下次快速跳过明显不可达的候选，并用于诊断上报。

---

## 6.3 选路

### 排序

```
优先级 = 基础优先级（候选类型决定，见 04 §4.2）
        ⊕ 偏移（上层策略覆盖）
```

| 类型 | 基础优先级 |
|---|---|
| IPv6 全局 | 10 |
| IPv6 link-local | 20 |
| IPv4 私有 | 30 |
| ZT | 40 |
| WAN | 5（若存在） |

**数值越小越优先。**

### 选定规则

1. 在**探测窗口内成功的候选**中，取优先级数值最小者
2. 若多个候选同优先级 → 取 **RTT 最小**者
3. 若窗口内无成功候选 → 进入降级流程

### 未选中候选的处理

**保留，不丢弃。** 每个未选中的成功候选进入「**温**」状态：

- 不维持长连接（省电、省资源）
- 记录其最近一次成功时间
- **网络变化事件触发时立即重新探测**

> 这是 ztio 与 ICE 最大的差异。ICE 选定后即丢弃其余候选；
> ztio 保留它们，因为**局域网路径随时会因换网络而失效**，
> 保留候选使自愈无需重走完整流程。

---

## 6.4 降级

```
① 探测窗口内 LAN 候选成功   → 用 LAN          （最优）
② LAN 全失败，ZT DIRECT 成功 → 用 ZT DIRECT
③ 只有 ZT RELAY 可用         → 用 ZT RELAY    （兜底）
④ 全部失败                   → ERROR
```

**降级是自动的、无损的**：应用层 API 与语义完全不变。

**关键约束**：降级**不能阻塞**数据面。
即使当前走的是 ZT RELAY，一旦某个 LAN 候选恢复正常，
**应当能够切回去**（见 6.5）。

### LAN 失败但 ZT 可用时的诊断

这种情况**必须记录并上报**，因为它的成因是二选一的：

| 成因 | 可观测证据 | 处置 |
|---|---|---|
| **客户端隔离（AP isolation）** | 探测超时（无 RST） | 无解，接受降级 |
| **权限被拒**（iOS/macOS） | 系统回调明确返回拒绝 | 引导用户授权 |

**两者表现不同，不能混淆**：权限问题可修复，隔离问题不可修复。
如果把它们混为一谈，用户会反复授权却毫无效果。

## 6.5 自愈

### 触发条件

| 事件 | 来源 | 动作 |
|---|---|---|
| 本机网络变化 | 系统回调 | 重新枚举 → `gen++` → 推送 `candidates-update` → 重探测 |
| 对端推送更高 `gen` | 信令 | 用新候选集重探测 |
| 当前路径失效 | 数据面检测 | 立即从温候选中选择备选 |
| 定期重探测 | 定时器（30s） | 轻量探测 LAN 候选 |

### 网络变化处理流程

```
系统回调：网络已变化
       │
       ▼
  重新枚举接口（gen++）
       │
       ▼
  推送 candidates-update 给对端
       │
       ▼
  并行重探测（本端全部候选 + 对端最新候选）
       │
       ├── 有更优路径（如 LAN 恢复）→ switch
       └── 无更优路径 → 保持当前路径，不中断
```

**关键设计**：**先探测，后切换。** 绝不断开当前路径去做探索。
这与「保留温候选」是配套的 —— 保证任何时刻都有可用路径。

### 防抖

移动端网络变化回调可能连续触发（信号弱时反复切换）。

| 措施 | 值 |
|---|---|
| `gen` 递增去抖 | 500 ms 内的多次变化合并为一次 |
| 重探测限流 | 两次完整重探测间隔 ≥ 2000 ms |
| 切换冷却 | 切换到新路径后 3000 ms 内不再切换 |

---

## 6.6 切换

### 何时切换

| 场景 | 是否切换 |
|---|---|
| 发现更优路径，当前路径仍健康 | ✅ 切换（如 ZT → LAN，省流量） |
| 发现更优路径，当前路径刚建立 < 3s | ❌ 等待冷却期 |
| 当前路径失效 | ✅ 立即切换（不等冷却） |
| 更优路径优一点点（同类型） | ❌ 不切换（避免抖动） |

**「更优」的判定必须留出滞回**：只有当新路径的优先级**严格更优**
（高一个档位以上）时才切换，同档位不切换。

### 切换协议

```
本端                              对端
 │                                 │
 │── switch {to, gen, reason} ────>│
 │                                 │ 确认候选可用
 │<──── switch-ack / error ────────│
 │                                 │
 │  两端同时把数据面切到新路径       │
```

**注意**：切换需要两端协调。若对端拒绝（该候选不在它的候选集中），
保持原路径并记录异常。

## 6.7 与「手机蜂窝出口」策略的关系

ztio 的路径选择只决定 **Mac ↔ 手机这一段走哪条路**。

「手机用蜂窝 IPv6 出口」是**应用层**的另一段转发逻辑，与路径选择正交：

```
Mac App ──[ztio 选出的路径]──> 手机 App ──[App 自己绑定蜂窝接口]──> 外网
              ↑                              ↑
         ztio 负责                     App 负责，ztio 不介入
```

**ztio 不感知、不干预出口选择。** 这保持了职责边界清晰。
