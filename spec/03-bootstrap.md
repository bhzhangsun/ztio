# 03 · 引导（Bootstrap）

## 3.1 要解决的问题

要用 ZT 链路交换候选，前提是**能连上对端**。但「连上对端」需要知道对端的 ZT 地址 —— 鸡生蛋。

**这就是引导要解决的唯一问题：`peerName → ZT 地址`。**

## 3.2 为什么这一层比局域网发现容易得多

| | 局域网 IP | ZT 地址 |
|---|---|---|
| 谁分配 | 上游 DHCP，随机 | **你的 controller** |
| 是否稳定 | ❌ 换网就变 | ✅ 加入网络后固定 |
| 是否可预知 | ❌ 无法预知 | ✅ **可编排、可预分配** |
| 有无固定入口 | ❌ 无 | ✅ **有：网络网关** |

**结论：这一层不需要「动态发现」，只需要「查表」。**

## 3.3 锚点模型

```
        ZT 叠加网（私有，加密）
   ┌──────────────────────────────────┐
   │                                  │
   │   ┌─────────────┐                │
   │   │  锚点        │  172.16.0.1    │  ← 地址固定，常开
   │   │  花名册      │  名字解析       │
   │   └──────┬──────┘                │
   │          │                       │
   │   ┌──────┴──────┐                │
   │   │             │                │
   │  Mac          手机                │
   │  172.16.0.12  172.16.0.11        │
   └──────────────────────────────────┘
```

**锚点的三条性质：**

| 性质 | 说明 |
|---|---|
| **地址固定** | 由 controller 静态分配（如 `172.16.0.1`），所有设备天然知道 |
| **只在网内可达** | 不暴露任何端口到公网 |
| **无状态即可用** | 花名册可以只是一个静态配置文件 + 自注册 |

**谁当锚点**：网络中任何一台常开设备。通常就是**网段网关**（`172.16.0.1`）——
它本来就在每台设备的配置里（作为 DNS 服务器和默认路由），不需要额外告知。

## 3.4 两种实现方式

### 方式 A：静态花名册（最简单，推荐起步）

锚点上维护一份配置文件：

```ini
# /etc/ztio/roster.conf
phone   = 172.16.0.11
mac     = 172.16.0.12
nas     = 172.16.0.1
```

- 设备启动时**不做任何查询**，直接用编译期/配置期注入的映射
- 适合**设备数量固定**的部署
- **零运行时依赖，零故障点**

> **什么时候够用**：设备总数固定、名字到地址的映射很少变。
> 大多数个人 / 小团队部署都属于这一类。

### 方式 B：动态注册（可扩展）

锚点提供一个**只在 ZT 网内监听**的 HTTP 端点：

```
POST /register   {"name":"phone", "ztAddr":"172.16.0.11", "ttl":300}
GET  /lookup?name=phone          → {"ztAddr":"172.16.0.11"}
GET  /roster                     → 全部在线设备
```

- 设备启动时注册自己，并定期续约（TTL）
- 适合**设备数量增长、地址由 DHCP 动态分配**的部署
- 需要处理：认证、TTL 过期、并发

**认证**：复用 ZT 网络本身的私有性 —— 端点只绑在 ZT 接口地址上，网外不可达。
若需更强保证，再叠加一层预共享密钥。

## 3.5 引导流程

```
① 设备入 ZT 网络（libzt: zts_node_start + zts_net_join）
② 等待网络就绪，拿到自己的 ZT 地址
③ （方式 B）向锚点注册自己的名字
④ 需要连对端时：查花名册得到对端的 ZT 地址
⑤ 经 ZT 地址建立信令会话 → 进入候选交换（见 05）
```

**③④ 的顺序可以颠倒**：先注册再查，或先查再注册，互不依赖。

---

## 3.6 失败与降级

| 失败点 | 表现 | 处置 |
|---|---|---|
| 锚点不可达 | 查不到名字 | 用**本地缓存的映射**重试；缓存过期则报「引导失败」 |
| 名字不存在 | 404 | **终止**，这是配置错误，不是网络问题 |
| 注册失败 | 超时 | **不阻断** —— 自己仍可发起连接，只是别人查不到自己 |

**设计原则：引导失败不应该是「整个不可用」。** 只要能查到对端，就不需要自己可被查到。

---

## 3.7 缓存策略

| 项 | 值 | 理由 |
|---|---|---|
| 映射缓存 TTL | 300s | ZT 地址极少变；长 TTL 减少锚点压力 |
| 失败后退避 | 指数，上限 60s | 避免锚点故障时打爆 |
| **局域网候选缓存** | **不缓存** | 局域网 IP 随 DHCP 变化，**每次连接前必须重新交换** |

> **最后一条是硬性要求。** ZT 地址可以缓存，**局域网候选绝对不能** ——
> 这是两者最本质的区别，混淆它们会导致「换 WiFi 后连不上」的经典故障。

## 3.8 与「局域网 DNS」需求的关系

用户的原始需求之一是：

> 支持局域网内 DNS，为网络内的某个节点配一个 DNS，在这个网段内用域名即可访问。

**花名册就是这件事的应用层推广**：从「人查域名」扩展到「App 查同伴」。

| | 内网 DNS（dnsmasq） | 花名册 |
|---|---|---|
| 服务对象 | 用户的浏览器 / 终端 | **App** |
| 查询方式 | `nslookup phone.zt` | SDK 内部调用 |
| 返回内容 | IP | ZT 地址 |
| 依赖 | 客户端配置 DNS 指向锚点 | 无（锚点地址编译期注入） |

**两者可以共存，互不冲突**：DNS 服务人，花名册服务 App。
如果部署里已有 dnsmasq，方式 A 的静态花名册可以直接从 DNS 记录生成。
