# 05 · 信令与状态机

## 5.1 信令通道

**信令通道 = ZeroTier 链路本身。** 没有独立的信令服务器。

```
Mac App                           手机 App
   │                                  │
   └──── ZT 链路（DIRECT 或 RELAY）────┘
              ▼
        承载 ztio 信令消息
        （长度可控，通常 < 2 KB）
```

**为什么可行**：信令只在**建连时**和**网络变化时**发生，数据量极小。
即使 ZT 退化到 RELAY，这点流量的成本也可以忽略 —— 而数据面走的是局域网。

**信令会话**：在 ZT 地址之上建立一条连接（TCP 或可靠 UDP），用于双向交换消息。
连接本身也走 ZT，所以天然加密、天然认证。

---

## 5.2 消息格式

所有消息为 JSON，带统一信封：

```json
{
  "v": 1,
  "sid": "7f3a9c21",        // sessionId，8 字节 hex
  "seq": 12,                 // 会话内单调递增
  "type": "offer",
  "body": { }
}
```

| 字段 | 说明 |
|---|---|
| `v` | 协议版本，不匹配则拒绝 |
| `sid` | 会话标识；变化即代表全新会话 |
| `seq` | 用于防重放与乱序检测 |
| `type` | 消息类型 |
| `body` | 类型相关载荷 |

## 5.3 消息类型

### `offer` — 发起方发送自己的候选集

```json
{
  "type": "offer",
  "body": {
    "peer": "mac",
    "gen": 7,
    "candidates": [
      {"type":"lan-v6","addr":"2408:8207::5","port":45231,"priority":10},
      {"type":"lan-v4","addr":"192.168.1.23","port":45231,"priority":30},
      {"type":"zt","addr":"172.16.0.12","port":45231,"priority":40}
    ]
  }
}
```

### `answer` — 应答方回应自己的候选集

结构同 `offer`，`type` 改为 `answer`。

### `candidates-update` — 候选集变更（单向推送）

```json
{ "type": "candidates-update", "body": { "gen": 8, "candidates": [ ... ] } }
```

**触发条件**：网络变化 → 重新枚举 → `gen++` → 推送。
**接收方必须**：立即重探测，并允许切换路径。

### `probe-result` — 探测结果反馈（可选优化）

```json
{ "type":"probe-result", "body": { "gen":7, "addr":"192.168.1.23", "ok":true, "rtt_ms":3 } }
```

用于对端提前知道哪些候选通、哪些不通，**省掉重复探测**。

### `switch` — 路径切换通知

```json
{ "type":"switch", "body": { "to":"lan-v4:192.168.1.23", "gen":8, "reason":"network-change" } }
```

**语义**：我准备切到这条路径了，请在它上面保持监听。
**接收方必须**：确认该候选在自己的候选集中**也**可用，否则拒绝并回退。

### `ping` / `pong` — 保活

```json
{ "type":"ping", "body": { "ts": 1736899200 } }
```

用于维持信令会话并检测其存活。**注意**：这与数据面的心跳是两回事。

### `error`

```json
{ "type":"error", "body": { "code":"no-common-path", "msg":"no candidate succeeded" } }
```

## 5.4 连接状态机

```
                  ┌──────────┐
                  │  IDLE    │  未入网
                  └────┬─────┘
        zts_net_join   │
                       ▼
                  ┌──────────┐
                  │ JOINING  │  等网络就绪 / 拿 ZT 地址
                  └────┬─────┘
             network-ok│
                       ▼
                  ┌──────────┐
                  │ BOOTSTRAP│  查花名册 peerName → ZT 地址
                  └────┬─────┘
             resolved  │   （失败：用缓存映射重试）
                       ▼
                  ┌──────────┐
                  │SIGNALING │  建立信令会话，交换候选集
                  └────┬─────┘
         candidates ×2 │
                       ▼
                  ┌──────────┐
                  │ PROBING  │  并行探测全部候选
                  └────┬─────┘
           first-ok    │   （全部失败 → ERROR / 退到 ZT 单路径）
                       ▼
                  ┌──────────┐
        ┌────────>│CONNECTED │  数据面运行中
        │         └────┬─────┘
        │              │ network-change / path-lost
        │              ▼
        │         ┌──────────┐
        └─────────│RESELECT  │  重新枚举 + 重交换 + 重探测
      better-path └──────────┘
```

### 状态职责表

| 状态 | 进入条件 | 动作 | 退出条件 |
|---|---|---|---|
| `IDLE` | 初始 | —— | 调用 `connect()` |
| `JOINING` | 已发起入网 | 等 libzt 网络就绪 | 拿到 ZT 地址 |
| `BOOTSTRAP` | 已入网 | 查花名册 | 解析成功 / 用缓存 |
| `SIGNALING` | 已解析地址 | 建信令会话、交换候选 | 双方候选集齐备 |
| `PROBING` | 候选集齐备 | 并行探测 | 任一成功 / 全部失败 |
| `CONNECTED` | 路径选定 | 数据面运行、保活 | 路径失效 / 网络变化 |
| `RESELECT` | 收到 change / 路径失效 | 重新枚举与探测 | 选出新路径 / 无路可走 |
| `ERROR` | 无法恢复 | 上报上层 | —— |

## 5.5 关键不变量

| # | 不变量 | 违反的后果 |
|---|---|---|
| I1 | **信令会话与数据路径生命周期独立** | 数据路径切换时信令不能断，否则无法协商 |
| I2 | **候选集必须双向交换**，不能单向 | 单向会导致对端无法在 LAN 上找到你 |
| I3 | **`gen` 只在候选集真正变化时递增** | 频繁递增会引发探测风暴 |
| I4 | **收到的候选集不持久化** | 隐私泄露 |
| I5 | **切路径前必须确认对端可接受** | 会切到对端不监听的地址 |
| I6 | **信令失败不等于连接失败** | 只要有一条可用路径，数据面就应继续 |

> **I1 最容易写错**：很多实现会把信令连接和数据连接做成同一条，
> 结果一切换路径就失去协商能力，无法再切回来。

## 5.6 版本与兼容

| 项 | 策略 |
|---|---|
| 版本字段 `v` | 不匹配 → 拒绝并回 `error`，**不尝试兼容** |
| 未知 `type` | **忽略**（前向兼容），不报错 |
| 未知字段 | 忽略 |
| 新增消息类型 | 只在大版本内加，靠「未知 type 忽略」保持兼容 |

**原则**：宁可拒绝一个不认识的版本，也不要猜测语义。
