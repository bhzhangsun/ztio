# 02 · 架构

## 2.1 分层

```
┌──────────────────────────────────────────────────────┐
│  L4  应用层        App 逻辑，只调 ztio.connect(peer)  │
├──────────────────────────────────────────────────────┤
│  L3  路径选择      按优先级尝试，先通则赢，失败降级     │
├──────────────────────────────────────────────────────┤
│  L2  候选集        LAN 候选（本机枚举）+ ZT 候选      │
├──────────────────────────────────────────────────────┤
│  L1  信令          经 ZT 链路交换候选集与状态          │
├──────────────────────────────────────────────────────┤
│  L0  ZT 传输       身份 / 加密 / 地址 / 兜底可达性     │
└──────────────────────────────────────────────────────┘
        ▲
        │ 引导（Bootstrap）：经锚点解析 peerName → ZT 地址
        └── 只发生一次，之后地址稳定
```

**每一层只依赖下一层。** 唯一的外部依赖是 L0 的 ZeroTier 部署。

---

## 2.2 四个抽象（与 ICE 的对应）

| ztio | ICE 对应 | 职责 |
|---|---|---|
| **Signaling** | 信令通道 | 交换候选集；在 ztio 中就是 **ZT 链路本身** |
| **Candidate** | Candidate | 一个可被连接的地址；由设备**自行枚举** |
| **Connectivity Check** | STUN Binding / 连接检查 | 对候选发起真实连接，测量可达性 |
| **Path Selection** | ICE 的 pair 排序与提名 | 按优先级选定一条路径，其余保留备用 |

**与 ICE 的关键差异**：

| | ICE | ztio |
|---|---|---|
| 信令通道 | 需要外部提供（SIP / WebSocket / 自建） | **ZT 链路自带** |
| 地址发现 | STUN 服务器告知公网映射 | **设备自行枚举局域网地址** |
| 未选中的候选 | 丢弃 | **保留为备用路径，随时可切** |

> **最重要的一条差异**是最后一行：ztio 不丢弃未选中的候选。
> 因为局域网路径随时可能因为换网络而失效，保留候选使**自愈**成为可能。

## 2.3 组件

| 组件 | 位置 | 职责 |
|---|---|---|
| **App** | 两端设备 | 调用 `ztio.connect(peerName)`；不感知路径细节 |
| **ztio SDK** | 两端设备 | 候选枚举 / 信令 / 连通性检查 / 路径选择 |
| **锚点 · 花名册** | ZT 网络内，地址固定 | 解析 `peerName → ZT 地址`；注册自己的名字 |
| **ZeroTier 传输层** | 叠加网 | 身份、加密、地址分配、信令通道、兜底数据通道 |
| **Planet / Controller** | 自建服务器 | 根服务与网络定义 |

### SDK 内部模块

| 模块 | 职责 | 详见 |
|---|---|---|
| `Bootstrap` | 查锚点，解析 peerName；注册自身名字 | 03 |
| `Candidates` | 枚举本机接口地址，构建候选集 | 04 |
| `Signaling` | 与对端交换候选集、维持心跳 | 05 |
| `Prober` | 对候选并行发起连接，报告结果 | 06 |
| `Selector` | 按优先级选路、触发降级与自愈 | 06 |

## 2.4 路径优先级

```
① 直连         IPv6 直连 / 局域网直连 / IPv4 直连   成本 0            ← 主路径
② ZT DIRECT    打洞成功，公网点对点                 双方上行           ← 次选
③ ZT RELAY     经 planet 中继                       服务器流量费       ← 兜底
```

**排序分两步**：先按**档**（决定成本），**档内按实测 RTT**（决定快慢）。

> **为什么档内不按地址族排**：IPv6 优先的理由是「没有 NAT、更可能成功」，
> 那是**可达性**的论据。一旦多个候选都探测成功，可达性已被证明，
> 此时**实测 RTT 是唯一真实的依据**。见 `06-path-selection.md` §6.3。

**可覆盖**：上层可通过策略强制指定（例如强制走蜂窝出口、或强制走 relay 以省电）。

**不变量**：无论走哪条路径，**应用层 API 与语义完全一致** —— 路径对上层透明。

## 2.5 数据流

### 建立连接

```
App ──connect(peerName)──> SDK
                             │
                    ① Bootstrap：查锚点，peerName → ZT 地址
                             │
                    ② 经 ZT 链路与对端建立信令会话
                             │
                    ③ 双向交换候选集
                             │
                    ④ 双向并行探测全部候选（两端各自向对方发起）
                             │
                    ⑤ 第一个成功且优先级最高的路径胜出
                             │
App <──Connected(path)───────┘
```

### 数据面

```
连接建立后：

  App ──> SDK ──> [选中的路径] ──> 对端 SDK ──> 对端 App
                    │
                    └─ 其余候选保持「温」状态（定期轻量探测），
                       当前路径失效时立即接管
```

**「温」状态的定义**：不持续占用连接，但保持候选地址的有效性记录，
并在网络变化事件触发时立即重新探测。

## 2.6 与部署的关系

```
ztio（应用层，本项目）
   │  依赖
   ▼
ZeroTier 叠加网（自建 planet + controller）
   │  运行于
   ▼
阿里云 ECS 8.137.163.130  +  各设备
```

**ztio 不关心 planet 在哪、有几台。** 它只要求：设备能入网、能互相可达（最差经 relay）。
这意味着**换一套部署，ztio 不需要任何改动** —— 只改 SDK 里注入的网络 ID 与锚点名字。

## 2.7 为什么不这样做

| 被否决的方案 | 否决理由 |
|---|---|
| 纯 mDNS / 广播发现 | 受限 AP 普遍屏蔽组播，**恰好是本项目要解决的场景** |
| 公网 rendezvous 服务 | 增加运维与单点；内网拓扑离开设备间加密链路；违反 G4 |
| 服务器下发「你的 IP」 | 设备自己最清楚；且服务器只知道公网映射，不知道局域网地址 |
| 串行按优先级尝试 | 首选项失败时要等满超时，用户感知为卡顿 |
| 丢弃未选中的候选 | 失去自愈能力；换网络后必须重新走完整流程 |
| 自研 P2P 传输 | 身份 / 加密 / 打洞 / 中继要全部自建，成本远超收益 |
